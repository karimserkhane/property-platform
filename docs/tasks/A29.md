# A29 — Captures déplacées vers le stockage objet sur la base partagée

**Pourquoi** : [A10](A10.md) a livré le code (`capture_storage relocate`, relecture transparente, contrôle dans `restore-check`) mais a laissé son exécution sur la base locale « à l'appréciation de Karim ». Elle n'a jamais eu lieu. Relevé en lecture seule du 31/10 (`manage.py capture_storage report`) : **9 538 captures et 1,84 Go dans PostgreSQL**, dont 3 784 captures et 1,63 Go déplaçables au-dessus du seuil de 64 Kio, et **0 capture** dans le stockage objet. Chaque sauvegarde quotidienne recopie donc ces octets ; la dernière mesure de sauvegarde date du 23/10 (468 Mo) alors que la base pèse 3,4 Go depuis les imports de l'émirat.

**Dépendances** : A10.

**Décision du propriétaire requise** : autoriser l'exécution de `relocate` par lots sur la base partagée (opération réversible par relecture, mais qui retire les corps SQL après copie vérifiée).

## Critères d'acceptation

- [x] Décision de Karim notée au journal.
- [x] Sauvegarde et `restore-check` verts juste avant le premier lot.
- [x] `relocate` exécuté par lots bornés (`--limit`), acteur nommé, hors d'un import ou d'un `rebuild-check` ; `report` relevé avant et après chaque série.
- [x] Taille de la base, durée et taille de la sauvegarde, et `restore-check` (objets vérifiés par taille et SHA-256) mesurés après ; résultats notés dans [MEDIA_STORAGE.md](../engineering/MEDIA_STORAGE.md) et [BACKUPS.md](../engineering/BACKUPS.md).
- [x] Une lecture de capture déplacée (fiche, référence, activité satellite) vérifiée identique après déplacement.

## Indications techniques

Commandes et seuils : [MEDIA_STORAGE.md](../engineering/MEDIA_STORAGE.md) (`capture_storage report|relocate`, `--min-bytes`). Les objets vont dans le volume `media-data` : ne jamais supprimer de volume. Le journal des lignes (`evidence.row_revision`, 1,8 Go) n'est pas concerné ; sa croissance est à noter dans la mesure.

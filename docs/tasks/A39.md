# A39 — Contrôles Docker lançables en parallèle depuis plusieurs worktrees

**Pourquoi** : le dépôt est organisé pour que plusieurs agents travaillent en même temps (un worktree et une branche chacun, une tâche par PR, contrôles en `--no-deps`). Mais trois contrôles partagent une ressource au nom fixe, si bien que deux agents qui les lancent en même temps se gênent ou cassent le travail de l'autre :

- **`checks-api`** : les tests PostGIS créent et suppriment la base `test_property_platform` sur le serveur partagé (`infra/local/compose.checks.yaml`, commentaire de la ligne 8 ; nom de test par défaut de Django pour `property_platform`). Une seconde exécution détruit la base de test de la première.
- **`checks-web`** : les volumes nommés `checks-node-modules`, `checks-web-node-modules`, `checks-contracts-node-modules`, `checks-branding-node-modules`, `checks-web-next` et `checks-pnpm-store` sont communs à tous les worktrees. Deux exécutions installent ou compilent en même temps dans les mêmes dossiers, parfois avec un code différent.
- **Pile e2e de démonstration** : `infra/local/compose.e2e-demo.yaml` porte le nom de projet fixe `property-platform-e2e-demo`. Une seconde pile remplace la première.

Besoin exprimé par Karim le 31/10 : pouvoir faire avancer deux IA en parallèle sans qu'elles se passent la main pour les contrôles.

**Dépendances** : aucune.

## Critères d'acceptation

- [x] `checks-api` utilise une base de test propre à chaque exécution (par exemple suffixée par un identifiant d'exécution ou de worktree), supprimée à la fin même en cas d'échec ; un reste d'exécution interrompue est identifiable par son nom et nettoyable par une commande documentée, sans jamais toucher à `property_platform` ni aux bases `rebuild_check_*` et `restore_check_*`.
- [x] `checks-web` n'écrit plus dans des volumes communs à tous les worktrees : volumes propres au worktree (nom de projet Compose ou suffixe), ou une installation partagée en lecture seule plus une sortie de compilation propre ; la réinstallation reste possible avec le certificat documenté dans [TOOLCHAIN.md](../engineering/TOOLCHAIN.md) malgré l'interception TLS d'Avast.
- [x] La pile e2e de démonstration accepte un nom de projet par exécution, ou le guide dit clairement qu'elle ne se lance qu'une fois à la fois ; aucun port de l'hôte partagé.
- [x] Essai réel : `checks-api`, `checks-ingestion` et `checks-web` lancés en même temps depuis deux worktrees, tous verts, sans effet sur la base en service ni sur les conteneurs partagés ; durées relevées.
- [x] La CI GitHub garde le même comportement (un job par contrôle, base jetable).
- [x] [AGENT_WORKFLOW.md](../engineering/AGENT_WORKFLOW.md) §4, [E2E.md](../engineering/E2E.md) et les commentaires de `compose.checks.yaml` à jour, y compris le nettoyage des volumes et bases propres à un worktree supprimé.

## Indications techniques

- Base de test : `DATABASES["default"]["TEST"]["NAME"]` dans `apps/api/src/property_platform/config/settings/testing.py`, lu depuis une variable d'environnement passée par `compose.checks.yaml` (l'hôte du conteneur ou un identifiant généré par `scripts/checks/api.sh` conviennent). Le rôle `property_platform` doit garder le droit de créer une base.
- Volumes : un nom de projet Compose dérivé du dossier du worktree isole naturellement les volumes ; vérifier que `--no-deps` vise toujours le service `db` du projet partagé (réseau et nom d'hôte) et ne crée pas une seconde base.
- Ne jamais supprimer un volume existant sans l'accord de Karim : les anciens volumes `checks-*` restent jusqu'à sa décision.

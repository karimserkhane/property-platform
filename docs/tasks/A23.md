# A23 — Statut de droits de chaque ligne de la base

**Pourquoi** : Karim veut, pour toutes les données, un statut de droits et de licence
lisible en base, tout en continuant à tout collecter et à tout afficher ([A22](A22.md)).
Depuis [A19](A19.md), chaque donnée hérite des droits du site d'où elle a été lue, mais
ce lien n'est calculé que dans le code Python. Aucune requête SQL ne dit « quels droits
pour cette ligne », et certaines tables ne sont reliées à aucun droit.

**Dépendances** : A22.

## Constat (29/10, base partagée)

- 9 146 captures et 27 tables de données reliées à une capture. 75 % des captures (66
  sites) ont une licence encore inconnue ([A21](A21.md)).
- Sans statut :
  - 17 zones de marche, dont la capture pointe vers la documentation de Valhalla ;
  - les 7 tables `real_estate` (parcelles, bâtiments, lieux, rues, zones, projets,
    promoteurs), reliées aux droits seulement à travers leurs lectures.
- L'interrupteur de publication n'existe que dans le dépôt : la base ne sait pas si une
  donnée est affichée au-delà des conditions de son site.

## Décision du propriétaire

27/10 : « garder toutes les données avec leurs pipelines, mais avec une colonne pour
indiquer la licence ou le droit ; je te laisse choisir la bonne pratique pour toute la
base et tout le code ». 29/10 : « pour toutes les données, une colonne d'audit droit et
licence qui donne le statut, mais tu collectes quand même et ça s'affiche sur la
plateforme ».

Bonne pratique retenue par Claude :
- **Pas de copie par ligne.** Une copie vieillirait à chaque revue. Le statut est
  calculé à la lecture, depuis la capture de chaque ligne et la revue en vigueur.
- **Une vue d'audit**, `evidence.data_rights` : une ligne par donnée et par capture d'où
  elle a été lue, avec licence, collecte, publication, date de revue, et les drapeaux
  « collecté malgré les conditions » et « affiché au-delà des conditions ».
- **Les calculs faits sur place** (zones de marche) héritent des droits de leur source
  d'origine, par la capture parente.

## Critères d'acceptation

- [x] Interrupteurs de `source_rights_enforcement.json` copiés en base
  (`evidence.source_rights_enforcement`) avec leur historique, par la même
  synchronisation que le registre.
- [x] Vue `evidence.data_rights` couvrant chaque ligne de chaque table de données des
  schémas `evidence` et `real_estate`, et vue de synthèse `evidence.data_rights_summary`.
- [x] Une capture d'un site non listé hérite des droits de sa capture parente listée ;
  sinon elle reste non qualifiée (`unknown`, `facts`), comme dans le code Python.
- [x] L'inventaire de l'historique (`pipeline_inventory.py`) refuse une table sans
  chemin vers ses droits ni exemption motivée ; le contrôle `data-history` échoue alors.
- [x] Tests PostGIS : héritage par hôte et par capture parente, lignes connues par un
  lien, interrupteur, revue modifiée sans réécriture, couverture des tables.
- [x] Documentation : DATA_PROVENANCE, REPOSITORY.
- [x] Contrôles CI verts sur la PR.

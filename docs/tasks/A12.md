# A12 — Reconstituer les versions historiques des interprétations

Issue du contrôle A04 : les captures recréent les 183 projets, mais les importateurs
actuels dédupliquent ou interprètent autrement des versions qui avaient été ingérées
avec d'anciens registres/extracteurs. Rejouer les octets avec le code actuel ne suffit
pas à prouver la reproduction de toutes les anciennes interprétations.

## Critères d'acceptation

- [ ] Identité durable de la version de registre et d'extracteur utilisée pour chaque
  interprétation ; conserver les anciennes assertions et leurs preuves.
- [ ] Rejeu des versions de fiches/catalogues, typologies, équipements et références
  médias ; tests des champs présents uniquement dans une ancienne version.
- [ ] Vérifier les valeurs publiées et leur provenance, en plus des comptes par table ;
  justifier toute différence légitime sans recopier le catalogue attendu.
- [ ] `rebuild-check` couvre ces versions et ne signale plus de perte inexpliquée.

## Journal

23 octobre 2026 — Claude Code, revue de la PR #11 (proposition, **décision du
propriétaire requise avant de changer les critères**). Mesure sur la base de service :
les 933 snapshots ont 933 captures distinctes, toutes exportées et rejouées avec succès
(940 étapes `project_details`), mais seulement 522 contenus distincts par projet ; le
rejeu en recrée 564. L'écart vient surtout de recollectes d'octets identiques et
d'anciennes versions d'extracteur, pas d'un fait perdu démontré. Tant que les comptes
d'historique sont comparés exactement, `rebuild-check` ne peut devenir vert qu'en
reproduisant chaque ancien extracteur. Proposition : ajouter un second niveau qui
compare l'**état publié** (fiches et leurs valeurs sourcées, parcelles actives, liens
d'identité actifs) et qui doit être vert, en gardant les comptes d'historique comme
alerte pour A11/A12. Rien n'est changé dans le contrôle en attendant cette décision.

# D03 — Canal d'envoi des alertes

**Pourquoi** : le livrable de la phase D du [plan concurrentiel](../product/PLAN_CONCURRENTIEL_20261023.md) est une « alerte reçue sur téléphone après un changement réel ». [D02](D02.md) décrit le suivi, le regroupement et un « flow Prefect d'envoi », mais aucun canal n'est choisi : un e-mail exige un fournisseur d'envoi et un domaine, une notification téléphone exige une application ou un service de notification. Ce choix engage coût, identifiants et données personnelles ; il revient à Karim.

**Dépendances** : D01 (comptes et consentement).

**Décision du propriétaire requise** : canal (e-mail, notification web, application), fournisseur et budget, domaine d'envoi.

## Critères d'acceptation

- [x] Décision de Karim notée au journal (déléguée le 07/11).
- [ ] Adaptateur d'envoi dans le module `accounts` ou un module dédié, identifiants hors dépôt, aucun envoi sans consentement enregistré ; désabonnement en un clic.
- [ ] Envois idempotents (une alerte n'est jamais envoyée deux fois), échecs visibles dans Prefect, budget borné.
- [ ] Essai réel : une alerte de test reçue sur le téléphone de Karim.

## Indications techniques

AGENTS.md : aucun service payant ni identifiant de production sans accord explicite. Le module `accounts` est le seul détenteur de données personnelles (plan §7).

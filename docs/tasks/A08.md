# A08 — Version de cache par famille de tables

**Pourquoi** : Toute écriture invalide tout le cache ; les collectes chaque minute le renouvellent sans cesse.

**Dépendances** : aucune.

## Critères d'acceptation

- [x] Version par famille de tables à partir de `evidence.row_revision` (index adapté), sans perte de l'exactitude.
- [x] Tests : une écriture sur une famille n'invalide pas les autres ; une exclusion invalide bien la lecture concernée.

## Indications techniques

Voir `api/read_cache.py` et la section cache de ENGINEERING_ROADMAP.

## Journal

- 2026-10-26, claude, `claude/A08-cache-families`, PR #32 : version par famille de tables.
  - Fait : `api/read_cache.py` relève la famille de chaque adresse (tables parcourues d'après `pg_stat_xact_user_tables` transaction par transaction pendant la lecture) et garde son corps tant que la dernière révision visible de chaque table de la famille et les transactions en cours au moment de la vérification n'indiquent aucune validation dans la famille. Repli sur l'instantané global si une table lue n'a pas de journal ou si la famille a changé pendant la lecture. Migration `evidence/0036_row_revision_cache_indexes` (index `(schema_name, table_name, id)` et `(transaction_id, schema_name, table_name)`). Voir [ENGINEERING_ROADMAP](../engineering/ENGINEERING_ROADMAP.md#version-par-famille-de-tables--26-octobre-2026-a08).
  - Tests : écriture dans une autre famille (corps et ETag gardés, vue non relancée), écriture dans la famille, exclusion sur l'annuaire des projets, transaction concurrente validée après la mise en cache avec un identifiant de journal plus ancien (vérifié par mutation : sans la vérification des transactions en cours, le test reçoit un `304` périmé).
  - Mesure : familles réelles relevées sur la base locale (lecture seule) ; `capture` et `ingestion_run`, écrites à chaque collecte, sont dans la plupart des familles. Suite créée : [A16](A16.md).
  - Numéro de migration : la PR #30 (C01, en attente de décision) ajoute aussi une migration evidence `0036` ; celle qui sera fusionnée en second devra être renumérotée (ou recevoir une migration de fusion), à signaler dans sa PR.
  - Constat de Codex (ci-dessous) : une transaction d'une autre base du même serveur figure dans l'instantané global mais n'écrit jamais dans ce journal ; elle n'invalide plus un corps gardé par famille et sort de la liste des transactions en cours dès sa fin.
  - Choix : la transaction de mesure ne s'ouvre qu'à la première requête de données hors transaction (une requête rejetée par la validation n'ouvre toujours aucune connexion) ; les lectures faites dans une transaction propre à la vue sont comptées instruction par instruction, sur un curseur séparé. Un `SET LOCAL` d'une vue ouverte après coup dure alors jusqu'à la fin de la lecture.
  - Contrôles : `checks-api` complet vert (614 tests PostGIS, aucune migration manquante, contrats à jour, frontières de modules), `pnpm docs:check` sur l'hôte. Non lancés : `checks-ingestion` et `checks-web` (aucun fichier d'ingestion ni web modifié ; la CI les lance).

# A17 — Délai dépassé de l'index des parcelles dans le job CI e2e

**Pourquoi** : le job `e2e` a échoué sur deux push de la branche de référence (runs
40236920659 et 40243799643, 25/10), alors que le même code passait sur la PR. Le
parcours `context-tiles.spec.ts` voit « These details could not be loaded. » : l'API
répond `503` à `GET /api/v1/preview/parcel-index?bbox=54.4,24.465,54.445,24.5`, la
lecture des parcelles ayant dépassé son `statement_timeout` de 2 s
(`psycopg.errors.QueryCanceled`).

**Dépendances** : A13.

## Critères d'acceptation

- [x] Cause mesurée sur la pile de démonstration (plan, statistiques, charge), pas
  supposée : statistiques absentes après le chargement, cache froid, plan ou délai.
- [x] Correctif qui ne relâche aucune garantie de production : délai de 2 s inchangé,
  aucune relance qui masquerait une lenteur réelle.
- [x] Parcours verts en local dans des conditions CPU qui reproduisent l'échec ;
  `E2E.md` à jour.
- [x] Job CI `e2e` vert sur la PR.

## Indications techniques

Voir [E2E.md](../engineering/E2E.md), `infra/local/compose.e2e-demo.yaml`,
`catalog/queries.py` (`parcel_features`) et `evidence/rebuild/demo_package.py`.

- 2026-10-26, claude, `claude/A17-e2e-parcel-index-timeout`, PR #36.
  **Échecs réels** : seulement les deux runs du 25/10 (sur ~32 jobs `e2e` exécutés) ;
  les six échecs `e2e` de PR du 26/10 sont des jobs que GitHub n'a pas démarrés
  (paiement ou limite de dépense du compte). Trace Playwright du run 40236920659 : les
  quatre quarts de `parcel-index` partent avec 18 tuiles z14, abandonnées par le
  navigateur 180 ms plus tard mais exécutées jusqu'au bout par l'API (le relais Next ne
  transmet pas l'abandon), et l'index de contexte ; le quart dense (2 060 parcelles)
  reçoit `503` après 2,35 s.
  **Hypothèses écartées, mesurées sur la pile de démonstration** : statistiques —
  `parcel` n'en a aucune après le chargement (`reltuples = -1`) jusqu'au premier
  passage de l'autovacuum, environ 10 s après « prête », mais le plan reste un parcours
  de l'index GiST : 87 ms sans statistiques, 81 ms avec (`EXPLAIN ANALYZE`), et ce
  passage coûte 0,85 s de CPU pour toute la base ; un `ANALYZE` après chargement ne
  changerait rien. Cache : base en tmpfs, tout en mémoire partagée ; le seul coût « à
  froid » est par session PostgreSQL (chargement de PostGIS ~25 ms, initialisation
  géographique ~18 ms), payé à chaque requête puisque l'API ouvre une connexion par
  requête. Requête : ~120 ms dans une session neuve au repos, dont 50 à 95 ms de
  `ST_Area(geography)` ; plan correct.
  **Cause** : `runserver` exécute toutes les requêtes de la rafale à la fois, chacune
  avec sa session. Reproduction déterministe : rafale du run en échec (4 quarts, 18
  tuiles, index de contexte) rejouée contre une API neuve, base et API sur 2 CPU, avec
  ou sans une charge CPU égale à celle du navigateur. Sous `runserver` : `503` du quart
  dense dans 10 essais sur 10 avec la charge ; sur 25 rafales, 43 lectures annulées et
  `parcel_features` jusqu'à 1,98 s (p90 1,55 s), et 0,8 à 1,9 s même sans charge
  externe. Sous gunicorn (4 threads, `CMD` de l'image) : aucune annulation, 0,87 s au
  plus (p90 0,56 s), y compris avec la charge.
  **Correctif** : `compose.e2e-demo.yaml` lance l'API sous gunicorn, comme l'image,
  avec la durée de chaque requête dans le journal d'accès. Délai de 2 s, requêtes,
  index, pile locale et production inchangés ; aucune relance.
  **Contrôles** : `checks-api` (619 réussis, Ruff, frontières, migrations, contrats),
  `checks-ingestion` (245), `checks-web` sans l'installation (Biome, contrats,
  TypeScript, 135 tests web ; `pnpm install` échoue dans le conteneur sur
  `UnknownIssuer`, interception HTTPS d'Avast, aucun fichier web modifié), `pnpm
  docs:check` sur l'hôte, `checks-e2e` contre l'API locale (premier lancement : 2
  parcours carte en échec sans qu'aucune requête n'atteigne l'API, relance 15 sur 15),
  pile de démonstration comme en CI (15 sur 15 ; sur 2 CPU : 3 fois 15 sur 15).
  Non fait : stocker la surface des parcelles diviserait environ par deux le coût de
  cette lecture, mais c'est un changement de schéma sans besoin mesuré hors de la CI.
